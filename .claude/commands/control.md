# Контроль: глубокий аудит репозитория Kaplia

**Ultrathink.** Это не быстрая проверка — это медленное, дотошное чтение чужого (моего) кода с подозрением, что в нём есть незамеченные косяки. Ошибки, на которые не обращает внимания обычная сессия: галлюцинированные API, расхождения между докой и кодом, мёртвые ссылки, недописанная логика, утёкшие секреты.

Цель — не починить, а **найти и составить отчёт**. Чинить только если пользователь явно попросит после ревью.

## Принципы аудита

1. **Trust nothing, verify everything.** Любое утверждение в `.md`-файлах — проверь по коду или `gh`. README говорит «two-tier LLM»? Найди routing-логику. Если её нет — это **расхождение**, не «фича на будущее».
2. **Доказательства > интуиция.** Каждая находка должна сопровождаться `file:line` или конкретной командой воспроизведения.
3. **Серьёзно к секретам.** Любая строка похожая на API key / token / private key / keystore content — проверь, нет ли её в истории git (`git log -p -S "<строка>"`).
4. **Не делай assumptions про время.** «Раньше работало» / «потом поправим» — не оправдание. Если в коде сейчас баг — он баг.
5. **Не пугайся быть занудой.** Лучше 30 мелких находок, чем 5 «крупных» и пропущенный SQL injection.

## Что проверять (план обхода)

### 1. Целостность фактов

- **ADR vs код.** Каждый ADR в `docs/decisions/` утверждает что-то конкретное. Найди реализацию или её отсутствие. Если ADR помечен `accepted`, но кода нет — это нормально на pre-MVP, но должно быть отражено где-то как pending.
- **README claims.** Бейджи, статус, описание стека. Бейдж CI ссылается на правильный workflow? Стек в README соответствует `build.gradle.kts`?
- **docs/analytics.md vs код.** События задекларированы — реализованы ли как `AnalyticsEvent`-классы? Custom keys, заявленные в `docs/analytics.md`, выставляются ли в коде?
- **CONTRIBUTING.md vs реальность.** Заявленные команды (`./gradlew ...`) работают? Hook путь существует? Branching strategy совпадает с branch protection на GitHub (`gh api repos/.../branches/main/protection`)?
- **Issue/PR-шаблоны.** Лейблы, упомянутые в шаблонах, существуют в репо (`gh label list`)? Папки/файлы, на которые ссылаются `Acceptance Criteria`, существуют?

### 2. Cross-references

- Markdown-ссылки внутри проекта: `grep` все `[text](path)` и `[[name]]` — каждый путь существует?
- `Closes #N` и `#N` в issues/PRs/коммитах — существуют ли эти номера? Не закрыт ли issue вне репа?
- `area:*`, `priority:*`, `type:*` в шаблонах vs `gh label list`.
- `CODEOWNERS` (если появится) — упомянутые юзеры существуют?

### 3. Безопасность

- В индексе git нет ли файлов из `.gitignore` (например, `google-services.json`, `*.jks`, `.env`)? Команда: `git ls-files | grep -iE '(keystore|secret|google-services|\.env|\.pem|id_rsa)'`.
- В истории — нет ли коммитов с PII / токенами? Проверь хотя бы по типичным паттернам (`AKIA[0-9A-Z]{16}`, `gh[opsu]_[A-Za-z0-9]{36}`, `xox[baprs]-[A-Za-z0-9-]+`, `-----BEGIN`).
- GitHub repo settings: `secret_scanning` включён? (`gh api repos/vadimkolobanov/kaplia | jq .security_and_analysis`).
- Branch protection реально не позволяет force-push на main? (verify через API, не по README).
- Workflows: используют ли `pull_request_target` (опасно)? Передают ли `secrets.*` в untrusted job-ы?

### 4. Код (когда появится — пока почти пустой)

- **Hardcode-строки на русском вне `strings.xml`.** `grep -rn "[а-яА-Я]" app/src/main/java/` — каждое совпадение должно быть аргументом для строкового ресурса.
- **Hardcode-числа** (sleep, таймауты, размеры) — должны быть в constants/конфигах.
- **Висящие TODO / FIXME / HACK** — список с приоритетом.
- **`Log.d` с возможным PII** в production builds.
- **Use of `!!`** в Kotlin без обоснования.
- **runBlocking в production коде.**
- **Suspicious permission usage** в `AndroidManifest.xml` (BIND_ACCESSIBILITY, SYSTEM_ALERT_WINDOW, и т.п.).
- **Незакрытые ресурсы / coroutine scopes без cancellation.**
- **Compose: unstable parameters** (lambda без `remember`, mutable objects).

### 5. Конфиги и зависимости

- `gradle/libs.versions.toml` vs реальные deps в `build.gradle.kts`. Согласованы?
- Версии библиотек: есть ли явно устаревшие (старше Gradle release - 1)?
- Pinning: Dependabot настроен на `develop` (после fix в #13)?
- `.editorconfig` совпадает с ktlint правилами?

### 6. Git / GitHub state

- Локальные ветки без upstream: `git branch -vv | grep -v "\[origin"`.
- Stale local branches смёрджены/удалены на remote: `[gone]` в выводе.
- Untracked файлы, которые должны быть в .gitignore (например `.tmp_*`).
- Открытые PR/issues которые на самом деле сделаны (`gh pr list`, `gh issue list`) — кросс-сверка с состоянием кода.
- Milestones: задачи привязаны к правильной фазе?

### 7. Документация — внутренняя консистентность

- Концепт говорит что-то про permadeath / возрастные ограничения / гендер — это согласуется с ADR?
- ТЗ vs концепт vs CLAUDE.md — где разойдутся, там потенциальное расхождение реализации.

## Формат отчёта

В конце — **только отчёт**, без кода-правок. Структура:

```markdown
# Контроль: отчёт <дата>

Прошёл по: <список разделов>. Всего находок: N.

## 🔴 Критично (N)
### F-001: <короткое название>
- **Где:** `path:line` или `https://github.com/.../...`
- **Что:** факт
- **Доказательство:** команда или цитата
- **Почему критично:** последствие
- **Рекомендация:** конкретное действие

## 🟡 Важно (N)
…

## 🔵 Заметки (N)
…

## ✅ Проверено и в порядке (N)
Короткий список: то, что показалось подозрительным, но при проверке оказалось корректным. Это полезно — пользователь видит что я не просто проигнорировал.
```

Severity-критерии:
- 🔴 **Критично**: утечка секретов / нарушение privacy / build broken / security vuln / релиз сломан
- 🟡 **Важно**: расхождение между докой и кодом / отсутствует механизм заявленный в ADR / устаревшая зависимость с CVE / hardcode-строка / нарушение собственных conventions
- 🔵 **Заметки**: косметика / nitpicks / preferences

## Что делать НЕ нужно

- **Не править.** Только отчёт. Если что-то крайне опасно (типа утечка токена) — выдели жирным «требует немедленных действий», но всё равно жди подтверждения.
- **Не разворачивать в task list.** Это отчёт, не план работ. Пользователь решит что чинить.
- **Не дублировать существующие issues.** Если находка уже есть как issue — упомяни «(уже есть #N)».
- **Не пушить, не мёрджить, не коммитить, не закрывать issues.** Read-only режим.
- **Не использовать subagents (Agent tool).** Это отбирает context window и теряет точность для аудита.

## Объём

Если репо большое — приоритизируй:
1. Безопасность (всегда)
2. Расхождения дока↔код (всегда)
3. Cross-references (всегда)
4. Код — по diff'у от прошлой проверки или по measure-ободу для текущего размера

Если не уверен — спроси пользователя «фокус на X, Y или весь обход?» перед началом.
