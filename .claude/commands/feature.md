description: Начать работу над GitHub issue — создать feature-ветку от свежего develop по conventions проекта
argument-hint: "<issue-number>"
---

Аргумент пользователя в `$ARGUMENTS` — это номер issue, над которым он хочет начать работать.

## Что делать

1. **Проверить чистоту worktree.** Запусти `git status --porcelain`. Если есть staged/unstaged изменения — остановись и попроси пользователя их сначала закоммитить или застэшить (`git stash`). Untracked файлы вне `.gitignore` тоже флагнуть.

2. **Убедиться что мы на `develop` и она свежая.**
   - `git checkout develop`
   - `git pull --ff-only` (если упадёт — значит локальный develop разошёлся; разобраться отдельно)

3. **Сходить за метаданными issue.** `gh issue view $ARGUMENTS --repo vadimkolobanov/kaplia --json number,title,labels,state`.
   - Если issue закрыт — спросить пользователя, точно ли он туда хочет.
   - Из labels определить тип ветки:
     - `type:feature` → `feature/`
     - `type:bug` → `fix/`
     - `type:docs` или `area:docs` → `docs/`
     - `type:refactor` → `refactor/`
     - `type:chore` или `type:deps` → `chore/`
     - всё остальное → спросить пользователя

4. **Предложить имя ветки** в формате `<тип>/KAP-<N>-<slug>`, где `slug` — kebab-case из первых 3–5 значимых слов title (без эмодзи и стоп-слов: «и», «в», «на», «—», "the", "a"). Покажи имя пользователю, дай возможность поправить.

5. **Создать и переключиться:** `git checkout -b <имя>`.

6. **Финальное сообщение** пользователю в 2 строки:
   - «Ветка `<имя>` создана от `develop`. Изменения делай в нужных файлах.»
   - «Когда готово — `/ship`.»

## Чего НЕ делать

- Не делать `git push` сейчас — пока коммитов нет, нечего пушить.
- Не открывать никаких PR — это работа `/ship`.
- Не комментировать issue.
- Если worktree грязный — НЕ автоматически стэшить. Только подсказать команду пользователю.
