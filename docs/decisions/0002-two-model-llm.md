# 0002. Two-tier LLM: Haiku 4.5 для рутины, Sonnet 4.6 для ключевых сцен

- **Status:** accepted
- **Date:** 2026-05-19
- **Deciders:** @vadimkolobanov

## Контекст

Бюджет LLM на пользователя в месяц должен укладываться в exposure юнит-экономики (LTV ≥ 5× CAC). Если все диалоги гонять через Sonnet — стоимость взрывается на масштабе. Если все через Haiku — теряется глубина в эмоционально нагруженных моментах (рождение, смерть, наследование).

## Рассмотренные варианты

1. **Только Haiku 4.5** — дёшево, быстро. Отказ: ключевые сцены звучат банально.
2. **Только Sonnet 4.6** — качественно. Отказ: $$ при D30 retention 25% делает unit-economy убыточной на free tier.
3. **Two-tier: Haiku по умолчанию, Sonnet на «больших» сценах** — оптимум.
4. **Локальная модель (Gemma на устройстве)** — отложено: качество ниже планки, батарея/тепло.

## Решение

**Two-tier routing через Cloudflare Worker.**

- **Haiku 4.5:** ежедневные диалоги, реакции на телеметрию здоровья, мелкие события.
- **Sonnet 4.6:** рождение, имянаречение, смерть, наследование, кризисные диалоги (mental health triggers), Crystal stage откровения.

Routing-логика в `backend/cloudflare-worker/`, событие выбора модели логируется как `llm_tier` в Crashlytics custom keys.

## Последствия

### Позитивные
- Юнит-экономика держится при разумном retention
- Sonnet тратится там, где пользователь это запомнит
- Promp-каталог разделён по сложности — легче A/B-тестировать

### Негативные
- Усложнение бэкенда (routing + fallback между tier)
- Sonnet может быть недоступен → graceful fallback на Haiku обязателен

### Что станет сложнее
- Тестирование: нужны eval-сеты на оба tier
- Мониторинг качества: ratio Sonnet/Haiku должен быть зафиксирован
